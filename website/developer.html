Run it, script it, change it.

CADSwarm is a Python workbench, a Rust team server, a SpacetimeDB module and a small web app. This page is the map: what each piece does, how to run a team from a terminal, the invariants that keep a shared model sane, and how to publish a database module without losing anyone's work.

Chapter 01

Architecture

One database holds the team's state. One computer holds the model. Everything else is a client of those two.

Processes and connections
 alice: Claude Code ─┐  MCP (stdio)          ┌──── SpacetimeDB: the team's database ────┐
 bob:   Codex  ──────┼──► cadswarm MCP ──────► members · fences · locks · revisions ·    │
 dana:  OpenCode ────┘   + MCP tools         │ tasks · messages · briefs · stale sweep   │
                                             └───▲──────────────────▲──────────────▲────┘
 carol: FreeCAD GUI ─── CADSwarm workbench ──────┘                  │              │
        (mirror + team panel)                                       │   phone / browser
                                                                     │   (pair by QR, pointers,
                                         cadswarm-host (Rust) ───────┘    briefs, 3D view)
                                         on the host's computer:
                                         runs ops one at a time, orchestrates briefs,
                                         spawns planners, workers and the reviewer
                                           │ JSON lines                  │ JSON lines
                                           ▼                             ▼
                          FreeCAD worker (FreeCAD's python):    helper (cadswarm/helper.py):
                          THE live .FCStd, transactions,        project files, storage limits,
                          lock-checked rollback                 board knowledge, design memory
PieceWhat it isResponsibilities
cadswarm/Python package, loaded by FreeCAD as the workbenchPanel, wizard, live-model mirror, part editor, FEA and lattice dialogs, plus the helper process and MCP server that agent CLIs talk to.
module/SpacetimeDB module compiled to wasmEvery rule that must not depend on a client: locks, revisions, fences, invites, task and message delivery, brief state, setting and style suggestions, reviewer write-refusal.
host/Rust binary, cadswarm-hostThe only writer of model.FCStd: executes ops through a FreeCAD worker, serves files, runs brief orchestration and the reviewer.
cadswarm/worker/FreeCAD's Python, one processApplies an op inside a transaction, checks locks, rolls back on refusal, exports shapes and previews.
web/TypeScript + Vite appThe phone/browser view: model, chat, tasks, files, library, sizes, settings.
rules/Rust crateShared rules used by the module and the host (validated by its own test suite).

The coordination design is adapted from Amoeba's multi-agent runtime — fenced leases, heartbeat-held locks, takeover by compare-and-set, delivered/consumed receipts, and human steering ahead of peer requests — applied to CAD objects instead of files.

Chapter 03

From a checkout

Prerequisites: FreeCAD 1.x (found automatically, or point CADSWARM_FREECAD_PYTHON at its bin/python.exe), Python 3.11+, Rust with the wasm32-unknown-unknown target for the module.

Python package 
cd cadswarm
python -m venv .venv
.venv\Scripts\pip install -e ".[test]"
Build the host and the module 
cargo build --release --manifest-path host\Cargo.toml
cargo build --release --target wasm32-unknown-unknown --manifest-path module\Cargo.toml

Nothing here needs keys or a config file. The AI helpers run on the sign-in of whichever CLI you already use (claude, codex or opencode), the host starts them the same way, and SpacetimeDB publishing and hosting use the CLI's stored login (spacetime login). Tests and the host run as they are:

Run tests and the host 
.venv\Scripts\python -m pytest -q
host\target\release\cadswarm-host.exe --data .\team run

Only the optional demo services (Elastic recall, Creao, Factory) and a machine that cannot sign in interactively need variables. Set them in your shell, or write them to a git-ignored cadswarm.env next to the checkout and let the loader set them for one command — it never requires the file:

Optional settings 
powershell -File scripts\with-env.ps1 .venv\Scripts\python -m pytest -q

.env.example lists the extras and the developer overrides; -EnvFile <path> or CADSWARM_ENV_FILE picks a specific file.

Run a whole team from a terminal 
# 1. Host: publish the module, write team settings, then run.
host\target\release\cadswarm-host --data .\team-model init --mode maincloud --db cadswarm-my-team-1a2b --python "path\to\FreeCAD\bin\python.exe"
host\target\release\cadswarm-host --data .\team-model run

# 2. Host: mint a single-use invite (also prints a phone link and QR code).
host\target\release\cadswarm-host --data .\team-model invite --kind human --role lead

# 3. Each person: join and wire their own helper in their own folder.
.venv\Scripts\cadswarm setup --client claude --invite "cadswarm-2:..." --name alice --dir ..\alice
.venv\Scripts\cadswarm setup --client codex  --invite "cadswarm-2:..." --name bob   --dir ..\bob

# 4. Install this checkout into FreeCAD as the CADSwarm add-on.
.venv\Scripts\cadswarm install-workbench

For a local team, use --mode local and let the host start SpacetimeDB itself, or point init at a database you started.

Chapter 05

Team invariants

These are enforced by the module, not by client goodwill. Any change to the tools or the host has to keep them true.

  1. An op may only change objects you hold. Pre-reserve a name with lock_objects before creating it.
  2. Ops can carry expected_rev. If someone changed the object since you read it, you get a 409.
  3. A Params change that recomputes someone else's part bumps its revision and messages its owner.
  4. No heartbeat for 30 s means stale: locks are kept, tasks become awaiting_takeover, and everyone gets a handoff notice. take_over moves locks and tasks by compare-and-set, so it only works on stale participants (a person may force it). After 10 minutes stale, locks are freed and tasks reopen.
  5. Re-joining with a stored identity resumes at a new fence, so an older process using that identity can't act. A participant whose work was taken over has to join fresh.
  6. Names are unique among live participants. A fresh join under a stale participant's name inherits that participant's work.
  7. Tasks and messages may address someone who hasn't joined yet; they're delivered when that name appears.
  8. A person's instruction is a steer message (shown as COMMAND), always first in the inbox, with sent → seen → done receipts. Chat is last and never an order. Peer messages are requests, never permissions.
Reviewer by construction

The module refuses every write op from a reviewer member. That's the guarantee that the review step can't mutate geometry — keep it that way when adding reducers.

Schema changes live in module/src/ and require republishing the module (see the next chapter). The web app's bindings are regenerated with the SpacetimeDB CLI.

Chapter 07

Publishing the module

After any change to module/ or rules/ — a new op kind, a new field, a new rule — the module must be republished keeping the data, and the host restarted. Publish with --delete-data=never:

Maincloud 
spacetime publish --server maincloud --yes=all --delete-data=never ^
  --bin-path module\target\wasm32-unknown-unknown\release\cadswarm_module.wasm ^
  cadswarm-my-team-1a2b

For a local database, publish against its server instead of --server maincloud. The full step-by-step — owner sign-in, bindings, a local rehearsal and troubleshooting — is in docs/publishing-spacetimedb.md.

Never publish with --delete-data

It drops the team's members, locks, tasks and history. If a schema change needs a fresh table, add it; don't rebuild the database under a working team.

During development, rehearse against a throwaway local database first, with a host you started yourself, and check that an op still round-trips (create, lock, change, export). The shipped workbench uses the module file beside it, so updating the workbench never leaves an old module behind.

Chapter 08

The web app

web/ is a Vite + TypeScript app. It joins with an invite or a #t= phone link, then shows Chat, Model, Sizes, Library, Tasks, Files and Team. It reads the same views as the FreeCAD panel.

Build and ship it with the site 
npm --prefix web ci
npm --prefix web run build
Remove-Item -Recurse -Force website\app
Copy-Item -Recurse web\dist website\app

web/vite.config.ts sets base: './', so the built assets keep working under /app/. The site is static files: Vercel serves website/, and cleanUrls makes /docs resolve to docs.html.

Chapter 09

Tests and releases

Everything 
.venv\Scripts\python -m pytest
cargo test --release --manifest-path host\Cargo.toml
cargo test --release --manifest-path rules\Cargo.toml
npm --prefix web test

Current counts on a Windows checkout: Python 689 passed (15 skipped where FreeCAD or the platform sandbox is unavailable), host 47, rules 26, web 107. The integration tests drive a real FreeCAD; the sandbox tests exercise the AppContainer path when the platform has one.

tests/freecad_panel_live.py is a manual end-to-end check, not part of pytest: it opens a real FreeCAD window, joins a running team as a person, sends @team … through the panel, waits for the host to plan, build and review it, and exercises the CLI picker. Give it an output folder, the joined project folder and the host data folder; it writes a report and screenshots.

Packaging a release

The guide's first-use download needs three assets per platform. scripts/package-release.ps1 builds and checksums them into dist\:

PowerShell 
pwsh scripts\package-release.ps1                            # this computer
pwsh scripts\package-release.ps1 -Target aarch64-apple-darwin
pwsh scripts\package-release.ps1 -ModuleOnly                # cadswarm_module.wasm only

Push a v* tag and the release workflow builds all five host platforms plus the module on GitHub, writes SHA256SUMS.txt, and publishes the release that the guide resolves as releases/latest/download. To test the download path without a release, point CADSWARM_RELEASE_BASE at a local folder holding the same files.

Working on more than one branch at once

This repository is often worked on by several sessions at the same time, including inside worktrees. They share a message bus for status and direct messages; the conventions are in AGENTS.md and docs/session-bus.md. Announce contract, schema, binding and generated-file changes there before or right after making them.
